# ADR-0005: セッションウィンドウへのドロップによるホスト→ゲストのファイル転送

| Field | Value |
|-------|-------|
| Status | Proposed |
| Date | 2026-09-18 |
| Binds | spice-client |
| Decision makers | nlink-jp maintainers |
| Triggered by | 実ピアのゲートがファイル転送を検証できなかった。アプリが実装していないためであり、利用者が機能化を求めた |

## Context

SwiftSpice は vdagent のファイル転送プロトコルを実装している。`sendFile(at:name:)`、
`cancelFileTransfer(_:)`、そして queued / ゲスト承認待ち / progress / completed / cancelled /
failed を持つ `fileTransferEvents` ストリームである。アプリはそのどれも配線していない。
`Sources/` に参照は一切無く、両 README も対象外として挙げている。

このプロトコルの 2 つの性質が設計を決める。**押し出し専用**である。クライアントがゲストの
エージェントへファイルを送るのであって、ゲストからホストへの向きは存在しない。したがってゲストの
振る舞いでこのマシンにファイルが作られることはない。もう 1 つ、受け取ったファイルをどこに置くかは
ゲストが決める。クライアントは名前とバイト列を渡すだけである。

必要な上限はバックエンドが既に課している。送信元は通常ファイルであること（ディレクトリやデバイスは
拒否され、ディレクトリを走査することはない）、同時実行は 4 本まで、1 ファイルは 8 GiB まで、
ワイヤ上のチャンクは 16 KB である。

## Decision

### 1. 入口は 1 つ。接続中のセッションウィンドウへのドロップ

セッションウィンドウにファイルをドロップすると、そのセッションのゲストへ転送する。ドラッグが承認で
ある。これは ADR-0001 R1 が推測された意図の代わりに求めた、まさにその所作である。本アプリ自身の
ウィンドウ上で起き、対象ファイルを名指しし、ゲストやポータルのコンテンツには生成できない。

ランチャーは従来どおり `.vv` のドロップで接続を開始する。セッションウィンドウへのドロップは、
`.vv` ファイルであっても常に転送であり接続ではない。どちらの意味かは、操作者がドロップした
ウィンドウが語る。

セッションが未接続のとき、ゲストエージェントが使えないとき、ゲストがファイルを受け取らないと
広告しているときは、理由を示して拒否し、何も読まない。通常ファイル以外はバックエンドが拒否し、
同じ形で報告する。

設定による可否も、ファイルごとの確認も置かない。クリップボードはゲストが受動的に読めるので既定 OFF
だが、ここでは対象を名指しする所作なしには何も動かない。

### 2. 寿命と上限

`SessionController` がセッションごとのキューを持つ。同時 4 本はバックエンドの上限で、残りは待機し、
枠が空き次第開始する。10 個ドロップして 6 個が拒否される製品は役に立たないからである。各転送は
セッションウィンドウに名前・進捗・キャンセル操作とともに表示する。

切断はそのセッションの全転送をキャンセルする。キャンセルはトランスポートを閉じる前に同期的に
記録するので、実行中の転送が停止を妨げることはない。これは R7 を 2 つ目の種類の未処理作業に
適用したものである。転送は開始したセッションに束縛される。閉じたセッションのキュー項目は破棄し、
後の接続で送ることはない。

### 3. プライバシー

転送一覧はファイル名を表示する。操作者が選んだものだからである。診断サマリは表示しない。
`files_sent`、`files_failed`、`bytes_sent` の 3 つの計数だけを加える。ADR-0001 §6 は診断から
ファイルパスを除いており、名前も同じ種類の情報である。

### 4. 検証

実ピアのゲートのエージェントフェーズに、アプリ自身の経路を駆動するファイル転送テストを加える。
ゲストの `spice-vdagent` は `--file-xfer-save-dir` 付きで起動し、ゲスト側の監視ループが現れた
ファイルごとに `FILE_TRANSFER_RECEIVED name=<name> bytes=<n> sha256=<digest>` を記録する。
テストは既知の内容のファイルを一時ディレクトリから送り、名前とダイジェストを受領証に記録する。
ゲートは対応する行をゲストログに要求するので、合格はゲストが同じバイト列を持っていることを意味する。
拒否の経路（エージェント無し、ディレクトリ、未接続）はピアを要さないのでユニットテストで覆う。

## Consequences

- 操作者自身のデータをゲストへ送る最初の機能になる。承認は所作であり、境界は狭い。名指しされた
  通常ファイル、1 つのセッション、切断でキャンセル。
- 実ゲートは、シミュレーションに残る Ravada ポータルと、フィクスチャが作れないコーデックを要する
  H.264 を除き、アプリの全機能を覆うことになる。
- セッションウィンドウへ `.vv` をドロップすると「これをゲストへ送る」意味になり、ランチャーとは
  異なる。区別するのはウィンドウであり、README にそう書く。
- ゲスト側のファイル転送方針をここから制御することはない。拒否するゲストや、予想外の場所に保存する
  ゲストは、上書きするのではなく報告する。

## Alternatives considered

1. **メニュー項目とファイルピッカー。** 同じ操作に 2 つ目の入口を作り、その前にモーダルを置く。
   「これをこのウィンドウへ」に自然な所作はドラッグであり、ピッカーは求められれば後から足せる。
2. **ドロップごとの確認シート。** ドラッグは既に本アプリのウィンドウ上で対象を名指ししている。
   シートは判断を増やさずクリックだけを増やす。ADR-0001 は確認を接続の開始に留めている。
3. **クリップボードと同じ既定 OFF の設定。** クリップボードが既定 OFF なのは、操作者が動かなくても
   ゲストが読めるからである。ここでは所作なしに何も動かないので、設定は機能が黙って無効になる道を
   増やすだけである。
4. **同時実行の上限を超えた分を拒否する。** 単純だが、フォルダ 1 つ分をドロップする普通の場合に誤る。
5. **ゲスト→ホストの転送。** vdagent プロトコルに無い。WebDAV 共有が要るが ADR-0001 が対象外としている。
