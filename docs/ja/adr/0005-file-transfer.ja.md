## Context

SwiftSpice は vdagent のファイル転送プロトコルを実装している（`sendFile(at:name:)`、
`cancelFileTransfer(_:)`、`fileTransferEvents` ストリーム）。アプリはそのどれも配線していない。
`Sources/` に参照は無く、両 README も対象外として挙げている。

このプロトコルの 2 つの性質が設計を決める。**押し出し専用**である。クライアントがゲストのエージェントへ
送るのであって、ゲストからホストへの向きは無く、ゲスト由来の `start` / `data` は拒否される。したがって
ゲストが送るもので、このマシンにファイルが作られることはない。もう 1 つ、受け取ったファイルをどこに
置くかはゲストが決める。クライアントは名前とバイト列を渡すだけである。

バックエンドは通常ファイル以外を拒否し、ディレクトリを走査しない。その他の上限（同時 4 本、1 ファイル
8 GiB、チャンク 16,000 バイト）はコンストラクタの既定値であって、本アプリが選んだ強制ではない。初稿は
後者と取り違えていた。

## Decision

### 1. 入口は 2 つ。どちらも明示的。そして 1 つの拒否

**接続中のセッションウィンドウへのファイルのドロップ**が、そのセッションのゲストへ送る。
**セッション ▸ ファイルを送信…** はピッカー経由で同じことをする。セッションが入力フォーカスを持つ間、
ポインタは捕捉され隠されるので（デスクトップビューの `CGAssociateMouseAndMouseCursorPosition(0)` と
`NSCursor.hide()`）、捕捉を解除するまで掴むものが無いからである。抜け方を知らないと辿り着けない機能は、
辿り着けない機能である。

どちらの経路でも、操作者は本アプリ自身のウィンドウ上で対象ファイルを名指しする。それが承認である。
ADR-0001 が**接続**の開始前にネイティブ確認を求めたのは、そこでは意図が、ページ内容が生成しうる Web の
遷移メタデータから推測されていたからである（R1）。ここに推測は無い。ドロップやピッカーでの選択は、
自アプリのウィンドウに対する操作者の行為であり、「接続」をクリックするのと同種で、ゲストやポータルの
コンテンツには生成できない。この記録がファイルについてその問いに答える。ADR-0001 はこの点を語っていない。

**`.vv` ファイルはセッションウィンドウでは拒否**し、ランチャーを使うよう案内する。接続ファイルは SPICE
チケットを含み、ADR-0001 §2 はその表示も永続化も禁じている。ゲストへ送るのはそのどちらより悪い。
ランチャーは従来どおり `.vv` のドロップで接続を開始する。それ以外のファイルについては、操作者が
ドロップしたウィンドウが意味を決める。

セッションが未接続のとき、ゲストエージェントが使えないとき、ゲストがファイルを受け取らないと言っている
ときは、理由を示して拒否し、何も読まない。この判断は (urls, ライフサイクル, エージェントの可否) に対する
純粋関数なので、ドロップ処理が適用する規則そのものをテストが動かす。

**送ったバイトは取り消せない。** キャンセル、切断、終了は送信を止めるだけで、ゲストが既に持っている
ものを取り戻さず、書き込まれた部分ファイルはゲストに残る。転送一覧にそう表示する。

### 2. 所有・寿命・上限

転送は**接続**に属する。セッションオブジェクトではない。MJPEG 再試行の経路はトランスポートを畳んで
新しい `SpiceAgentManager` を作る一方、`SessionController` は生き残る。コントローラが持つキューは次の
接続で再開してしまう。したがって接続が終わる時点で全転送を失敗にし、イベント購読は新しいエージェントで
張り直す。

同時 4 本、残りは待機とする。フォルダ 1 つ分をドロップして超過分が拒否される製品は役に立たないからで
ある。この本数、1 ファイル 8 GiB、チャンク 4,000 バイトは `SpiceAgentManager` に明示的に渡す。本アプリ
の数値にするためである。

チャンクが小さいのは、エージェントチャネルがトークンによるフロー制御下にあり、依存側の既定値
16,000 バイトが QEMU の与える窓に収まらないからである。メッセージは 2 KiB のワイヤ断片ごとにトークンを
1 つ消費する。QEMU はトークンを 10 個与え、5 個ずつ返す。16,000 バイトのチャンクは 8 個必要なので、
2 つ目が 7 個の時点で永久に止まる。これは推論ではなく実測である。最初の実装は毎回ちょうど 64,000 バイト
中 32,000 バイトで停止した。

**進捗が止まった転送は 60 秒で失敗にする。** 依存側の 3 つの挙動がこれを飾りでなく必要にしている。
ゲストの capability が届く前に開始した転送は初期フェーズのまま、以後のイベントもタイムアウトも無い。
キャンセルは返ってこないかもしれないゲストの応答を待ちながら 4 枠の 1 つを握り続ける。イベントストリームは
最新 64 件をバッファするので、複数の転送が交錯すると終端イベントが捨てられうる。期限は最後に観測した
進捗から測るので、遅いが生きている転送は殺さない。

**停止処理の有界化はこちらで行う。** `SpiceAgentManager.stop()` は期限なしで実行中の操作を drain し、
`sendFile` はキャンセル不能な detached タスク内のブロッキング読み取りを跨いでそれを握る。よって停止した
マウント上のファイルは終了を無期限に止めうる。セッションはまず転送をキャンセルし、次に期限付きで
エージェントを待ち、期限が来たら構わず進む。未処理作業が停止を妨げないという R7 の規則を、依存が強制
しない場所で適用する。依存側の不足は隠さずここに記録する。ADR-0001 §6 の求めるとおりである。upstream 側で
drain を有界にするのは 3 本目の局所パッチであり、この決定には含めない。

### 3. 何を見せ、何を記録するか

ウィンドウはファイルごとではなく**ドロップごとに 1 行**を出す。件数、全体の進捗、そのドロップ全体を
止めるキャンセルである。失敗はその下に個別に名前を出す。「40 件中 3 件失敗」では名前が無く動けない
からである。映像面の上に 40 行並べるのは、組織の GUI ノートが警告しているまさにその形である。

転送一覧はファイル名を出す。操作者が選んだものだからである。診断サマリは出さない。`files_sent`、
`files_failed`、`bytes_sent` の計数だけを加える。ADR-0001 §6 がパスを除いているのと整合する。計数は
イベントで加算するのではなく転送一覧の状態から導くので、捨てられたイベントが値を壊すことはない。
発行していない id に対してゲストが上げた失敗は別に数え、どの転送にも帰属させない。

### 4. 検証

- 拒否規則は純粋関数で、ユニットテストを持つ。未接続、エージェント無し、ゲストが拒否、ディレクトリ、
  `.vv`、空のドロップ。
- 実ピアのゲートのエージェントフェーズに、アプリ自身の経路を駆動する転送テストを加える。ドロップ処理が
  呼ぶのと同じ判断関数を呼ぶ。既知の内容のファイルを一時ディレクトリから送り、受領証に
  `file <name> <sha256>` を記録する。
- ゲストの `spice-vdagent` は、この init が所有するディレクトリを `--file-xfer-save-dir` に指定して
  起動し、監視ループがファイルの**更新時刻**が 2 秒間変化しなくなった時点で
  `FILE_TRANSFER_RECEIVED name=<name> bytes=<n> sha256=<digest>` を報告する。必ず 1 行を出す強い期限も
  置く。vdagent はチャンクが届くたびに書くので、見つけ次第ハッシュを取る監視は部分ファイルをハッシュ
  するからである。最初の実装が使ったサイズの安定は何も証明しない。vdagent は最初のバイトが届く前に
  ファイル全体を確保するので、部分ファイルは既に最終サイズを持っている。エージェントがファイルを削除
  したときは `FILE_TRANSFER_REMOVED` を出すので、消えたファイルは沈黙ではなく報告された結果になる。
- ゲートは受領証とその行を突き合わせる。合格はゲストが同じバイト列を持つことを意味する。
  `live_peer_agent_log_matches` に 3 フィールド形式を足す。既存の走査は 2 フィールドでない行を飛ばすので、
  このままではこの検査が黙って空振りするところだった。3 フィールド形式はログ全体を探し、2 フィールド
  形式が進めるカーソルを動かさない。ゲストがファイルを報告するのは更新時刻が落ち着いた後、後続の
  マーカーより数秒遅れるからである。

### 5. 既知の限界。含みではなく明記する

- バックエンドは送信元をパスで stat し、その後パスで開き直す。`O_NOFOLLOW` は無く、ディスクリプタの
  再確認も無い。したがってシンボリックリンクは辿られ、2 回の間に差し替えられたパスは検査されずに開かれる。
  アプリは URL を渡す前にドロップを検証するが、ディスクリプタは保持しないので、これは依存側の境界であり、
  `.vv` リーダが自らの入力に課す境界より弱い。
- 送信中に編集されたファイルは、新旧のバイトが混ざって届く。サイズは開始時に固定され、内容は進行に
  つれてチャンクで読まれる。切り詰めは読み取り失敗として現れ、伸長は無視される。
- キャンセルはゲストに送られる（依存側が `CANCELLED` の状態を送る）。だが実ピアのゲートでは
  spice-vdagent がそれに応答しなかった（2026-09-22）。よって手元の部分ファイルをどうするかはゲストが
  決め、依存側は接続が終わるまでそのジョブと枠を持ち続ける（§7）。

### 6. 作って分かった 3 つの欠陥と、それぞれを直した場所

転送は毎回ちょうど 64,000 バイト中 32,000 バイトで止まった。ひとつの症状の裏に独立した原因が 3 つあり、
先の 2 つが 3 つ目を隠していた。

- **自分たちの ADR-0001 パッチが誤っていた。** クリップボード境界がアクセス拒否時に早期 return し、
  同じメソッド末尾のファイル転送と表示構成の駆動を飛ばしていた。自動ペーストボード同期が有効な間、
  このメソッドは唯一の周期経路である。つまりクリップボードを切ったセッションでは、タイマーによる転送の
  前進が一度も起きなかった。パッチを広げて直した。ローカルパッチは我々が所有する変更であり、これは
  ADR 2 つ分前から埋まっていた。
- **依存側の駆動は再入可能ではない。** 各パスはジョブを読み、読み取りと送信を await し、読んだ内容が
  そのままであるときだけコミットする。2 つのパスがその await で交錯すると互いを無効化し、どちらも
  コミットしないので同じオフセットを永久に送り直す。ゲストはそれを重複データとして拒否する。ここでは
  同時呼び出しは日常である。ペーストボードのポーリングが 250 ms ごとに転送を駆動し、受信するエージェント
  メッセージごとにも駆動する。アプリ側の回避ではなく 3 本目のローカルパッチ
  （`Vendor/file-transfer-drive.patch`）で直列化した。外からこの競合を避けられる呼び出し側は存在しない
  からである。
- **チャンク長がトークン窓に収まっていなかった。** §2 に記した通りである。これが真因であり、上の 2 つを
  直すまで姿すら見えなかった。

一般化できる教訓。きりのよい数値で止まるのは窓の問題であってバイト処理の不具合ではない。そして
ローカルパッチは被試験系の一部である。

`Vendor/*.patch` は `make verify-vendor` で固定した上流に対して再生され、記録したパッチが vendored
ツリーを組み立てられなくなったら失敗する。`check-project.py` は vendored の全ファイルと全パッチを
ハッシュで固定しているので、記録されていない編集は捕まえる。だがパッチがその編集を今も説明しているかは
判定できない。この作業を経てパッチは 3 本になった。

### 7. 追補（2026-09-22）: 枠は誰のものか、何を「止まった」とするか

監査が疑った欠陥 3 件のうち 2 件を、何も変える前に実ピアで再現した。3 件ともアプリ側で直し、
4 本目の vendored パッチは足していない。

- **待ち行列のファイルがタイムアウトしていた。** §2 の 60 秒の規則は、終わっていない項目すべてを
  最後の変化から測っていた。待ち行列の項目の最後の変化は作られた時刻である。最初の 4 本がタイムアウト
  より長くかかると、5 本目と 6 本目は送られないまま「止まった」で失敗した（1 MB × 6 本、タイムアウトを
  2 秒に縮めて再現）。今は送信中のファイルだけが止まりうる。
- **キャンセルが待ち行列を止めていた。** アプリはキャンセルした行を終わらせてすぐ枠を空けたが、
  依存側はゲストが応答するまでジョブを持ち続け、ゲストは応答しなかった。次の開始は依存側の上限に当たり
  「maximum concurrent file transfers reached」で失敗した（再現）。今は、終わった項目も依存側が
  ジョブの終わりを知らせるまで枠を持ち、その上限による拒否はファイルを待ち行列に戻し、止まった転送は
  依存側でもキャンセルする。§2 の「期限が対策」は誤りだった。見張りは依存側の枠を一度も空けなかった。
- **MJPEG の再試行が ID を使い回していた。** 新しいエージェントは転送に 1 から番号を振るが、古い行は
  自分の番号を持ち続けたので、新しい転送のイベントが古い行に届いた。今は、接続が終わるとすべての行が
  依存側の ID と枠を忘れる。再現はしていない（試験環境は H.264 からの切り替えを起こせない。verification.md）。

規則は純粋な関数（`FileTransferRules`）にして単体テストを付け、実ピアのゲートに
`sendsMoreFilesThanSlotsAndNoneWaitingIsFailedAsStalled` と `cancellingOneTransferLeavesTheQueueMoving` を
加え、ゲストがキャンセルに応答したかを記録する（`cancel-ack`。2026-09-22 は "none"）。帰結: キャンセルした
転送は、その接続の残りの間 4 枠の 1 つを使う。

## Consequences

- アプリは操作者のファイルをゲストへ送れるようになる。クリップボードのテキストは既に送っているので、
  操作者のデータが出ていく 2 つ目の経路であって最初ではない。違いは、ファイルは名前と内容をゲストの
  ディスクに残すことである。
- 実ゲートは、シミュレーションに残る Ravada ポータルと、フィクスチャが作れないコーデックを要する
  H.264 を除き、アプリの全機能を覆う。
- `.vv` は 2 つのウィンドウで異なる意味になる。ランチャーでは接続、セッションでは拒否。両 README に
  そう書く。
- 停止処理の期限はアプリのものであって依存のものではない。将来 upstream が drain をキャンセル可能に
  したら、ピン更新の際にこの期限を見直す。

## Alternatives considered

1. **ドラッグのみ。** 初稿。ポインタ捕捉中は辿り着けず、それは使用中のセッションの通常状態である。
2. **メニューのみ。** 辿り着けるが、自然な所作が何も起こさなくなる。ランチャーが既に「ウィンドウに
   ファイルを落とす」ことに意味があると教えている。
3. **ドロップごとの確認シート。** 所作は既に自アプリのウィンドウ上で対象を名指ししている。シートは判断を
   増やさずクリックだけを増やす。賭け金が拒否に値する唯一の場合（`.vv`）は、確認ではなく拒否にした。
4. **クリップボードと同じ既定 OFF の設定。** クリップボードが既定 OFF なのは、操作者が動かなくてもゲストが
   読めるからである。ここでは所作なしに何も動かないので、設定は機能が黙って無効になる道を増やすだけである。
5. **同時実行の上限を超えた分を拒否する。** 単純だが、多数のファイルを一度に落とす普通の場合に誤る。
6. **ゲスト→ホストの転送。** vdagent プロトコルに無い。WebDAV 共有が要るが ADR-0001 の Consequences が
   対象外としている。
