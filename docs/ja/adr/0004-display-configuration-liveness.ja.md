# ADR-0004: vendored パッチを広げ、モニタ構成の送信窓に期限を設ける

| Field | Value |
|-------|-------|
| Status | **Accepted** — 2026-09-18 ユーザー承認 |
| Date | 2026-09-18 |
| Binds | spice-client |
| Decision makers | nlink-jp maintainers |
| Triggered by | エージェント付きゲストのゲート（ADR-0003）が、エージェント接続でゲストに届くリサイズは最初の 1 回だけだと示した |

## Context

ADR-0001 は `Vendor/SwiftSpice` への局所変更を意図して狭く保った。パッチは 1 本、
クリップボード権限のみ。固定した upstream と突き合わせてレビューできる状態を保つためである。
同時に、依存の API が要求を満たせない場合は、隠さずに「依存側の変更が必要である」と記録せよとも
書いている。

実ピアのゲートが記録したのはまさにそれだった。`DisplayConfigurationCoordinator` は送信窓を 1 つ
持ち、構成が in flight の間はキューされた最新の 1 つだけを保持する。窓は `didReceiveReply`、
エージェント切断、`reset` で閉じる。`virtio-gpu` では QEMU が `VD_AGENT_MONITORS_CONFIG` を自身の
`client_monitors_config` ハンドラで消費し、`VD_AGENT_REPLY` を返さない（upstream のハーネスが
その旨を記している）ので、窓は決して閉じなかった。エージェント接続で最初のリサイズは届き、以後は
すべて捨てられ、その間も `resizingAvailable` は真のままなので、操作者には無言の故障になる。
再接続すると解けるため、手動利用では捕まらなかった。ゲートは QEMU 8.2.2 と 10.0.13 の双方で再現した。

窓そのものは残す価値がある。連続的なドラッグでゲストのエージェントを溢れさせないためであり、
アプリ側の 150 ms のデバウンスは利用側の好意であってライブラリが依存してよいものではない。

## Decision

2 本目の局所パッチ `Vendor/display-configuration-liveness.patch` を追加し、in flight の構成に
期限を与える。

- `DisplayConfigurationCoordinator.acknowledgementTimeout` は 2 秒。`didSend(_:at:)` が失効時刻を
  記録し、`nextToSend(now:)` はその時刻を過ぎればキューされた最新の構成を返す。応答・切断・reset が
  窓を閉じるのは従来どおり。
- 何もしていないときに生存性の代償は無い。失効した窓でもキューが空なら何も送らないので、ゲストが
  既に持っているものを再送することはない。効果は、相手が返す義務のない応答の後ろで新しい構成が
  永久に留め置かれなくなることだけである。
- 2 秒は、ドラッグ中も合体が仕事をし（未応答の構成は 2 秒に 1 つまで）、意図的な 2 回目のリサイズは
  期限のあと 1 ポーリング以内に届く値として選んだ。アプリ側のデバウンスで実際の間隔はさらに延びる。
- 窓の失効後に届いた応答は、その時点で in flight のもの、すなわち新しい構成を acknowledge する。
  イベント表示上の齟齬にとどまり、最新が勝つという結果は変わらない。防ぐのではなく、記す。

**出所の記録。** `Vendor/UPSTREAM.json` の `patches` を順序付きリストにし、各項目がファイル名、
SHA-256、導入した決定を持つ。各パッチは前のパッチが作った木に適用する。両パッチが
`SpiceClipboardManager.swift` に触れるため、この順序は意味を持つ。`check-project.py` は全項目を
検証し、変更した 3 ファイルのハッシュは従来どおり `files_sha256` を更新する。vendored な upstream の
テストは置き換えず拡張した。既存の合体テストは明示的な時刻を渡すようにし、タイムアウトが窓を解放する
ケースと、失効した窓でキューが空なら黙っているケースの 2 件を追加した。

**ゲートの固定を反転する。** ADR-0003 は欠陥を「検査される事実」として記録し、2 本目のモードが
現れないことを要求して、現れたら失敗するようにしていた。いまは 1 本目の後に 2 本目が順序どおり
適用されることを要求する。

## Consequences

- ビューポートのリサイズが、エージェント接続ごとに 1 回ではなく、セッションの寿命を通じて、
  どのトランスポートでも効くようになる。ADR-0001 が再設計した挙動のうち、実ゲートが壊れていると
  示した最後の 1 件がこれだった。
- 依存への局所変更は、もはや狭い 1 本のパッチではない。各々が導入した決定に紐づく 2 本になる。
  依存のレビュー可能性は保てるが、upstream を上げる際の費用は上がる。順序どおり両方を再適用する
  必要があり、上げる前のレビュー範囲に 2 つ目のファイルが加わる。
- upstream への提案は当面提出しない（upstream の運営実態を調べたうえで 2026-09-18 に判断）。
  仕組みの上では誰でも issue も pull request も作れる状態であり、欠陥は本プロジェクトが固定している
  まさにそのコミット、すなわち `main` の先端に生きている。しかし `CONTRIBUTING` も issue/PR の
  テンプレートも discussions も無く、fork は 0、維持者の 2 つの SPICE リポジトリの pull request は
  すべて本人が `codex/*` ブランチから出したもので、そのうち 3 件は 3 週間以上オープンのままである。
  単独かつエージェント主導の開発なので、同じ修正に自力で到達する見込みがあり、外部からの貢献が
  期待されている様子も無い。当面は局所パッチが修正を担い、upstream を再び見るのは監視ではなく
  次にピンを上げるときとする。
- ゲートが回帰を押さえ続ける。将来 upstream が別の方法で窓を閉じるようになっても、2 本目のモードを
  届けることは要求される。

## Alternatives considered

1. **新しい構成が即座に上書きし、窓を設けない。** 最も単純で、最新だけが意味を持つ状態メッセージには
   正しいが、ドラッグ中の氾濫防止が失われ、ライブラリがすべての利用者のデバウンスに依存することになる。
2. **相手が応答しないと検出し、その接続では以後ゲートしない。** 適応的で精密だが、学習するには未応答の
   要求が 1 つ必要で、それこそが後続を捨てられる当の要求である。状態を増やしたタイムアウトにすぎない。
3. **アプリ側で直す。** `SessionController` は依存の in flight 状態に手が届かない。できるのは
   エージェントを再接続して解除することだけで、ライブラリの欠陥を隠すために目に見える中断を起こす。
4. **upstream を待つ。** 出荷済みの製品に無言の故障を無期限に残す。ADR-0001 がまさにこの種の問題に
   対して、待つのではなく追跡可能な局所パッチを選んでいる。
